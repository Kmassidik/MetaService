# Contract

`openapi.yaml` is the API between the Root and every Agent. An Agent that passes the conformance tests works with
the Root, whatever language it is written in.

- `spec.py` loads the contract and validates JSON against it (used by the Fake Agent and the tests).
- `tests/` is the conformance suite. It runs against any Agent by address.
- `tests/run_fake.py` runs the whole suite against the Fake Agent in `agent/fake/`.
- `tests/mutation.py` checks the suite itself: deliberately broken Fake Agents must fail it.

Run inside the Nix dev shell (`nix develop`): `python3 -m contract.tests.run_fake` and `python3 -m contract.tests.mutation`.

## Versions

- Added without a version change (optional, macOS helper only; a helper without it answers 404): the console: helper WebSocket `GET /v1/workloads/{id}/terminal`, panel routes `POST /api/machines/{id}/workloads/{workload}/terminal` and `GET /api/terminal/{ticket}`. See `docs/console-contract.md`.
- Added without a version change (optional; a helper without it answers 404): the monitor: helper `GET /v1/stats` and panel route `GET /api/machines/{id}/stats`. See `docs/monitor-contract.md`. Later, also without a version change: the optional query `processes` (`1` or `0`, absent means `1`) on both routes; `0` skips the scan of programs (`processes: []`), other values are a 400.
- Added without a version change (optional; a helper without it simply leaves it out): on a workload, `stopped_reason` (`exit_code` or null, `log_tail`: why a VM that stopped by itself stopped) and `init_mode` (`systemd` or `plain`). A create that fails because the VM never came up carries the plain-words reason (and the last lines the VM printed) in the failed command's `result.error`. The Root returns both fields on every workload of `GET /api/machines` (null when empty).
- Added without a version change (optional; a helper without it simply leaves them out): more numbers in `GET /v1/stats` and in the panel route: `cpu.physical_cores`, `cpu.core_of`, `cpu.clusters`, `cpu.breakdown`, `cpu.frequency_mhz`, `cpu.temperature_celsius`, `network.errors_in_total`, `errors_out_total`, `drops_in_total`, `drops_out_total`, top-level `disk_io` and `process_count`, and `threads` on a program. The parent keeps each only when it is in range and leaves out what is not. New panel route `GET /api/machines/{id}/stats/history?points=N` (N 1 to 360, default 360): the last hour of readings kept in the parent's memory (about one every 10 seconds, only for online machines, lost on restart). See `docs/monitor-contract.md`.
- Added without a version change (optional; a helper without it answers 404, and the parent then treats the machine as having only `blank`): ready-made images. Helper `GET /v1/images` (what the machine has prepared: `{ "images": [ { "id", "ready", "built_at" } ] }`), panel routes `GET /api/images` (the parent's catalog: id, title, description, state `ready` or `planned`, reason) and `GET /api/machines/{id}/images` (catalog joined with the machine: `ready`, `available`, `reason`, and `helper` = `answered`, `old_helper` or `unreachable`), and the optional `bundle` (a catalog id) on `POST /api/workloads` and on the helper's `POST /v1/workloads`. On the panel route an unknown id is a 400 `invalid_input`, a listed but `planned` id is a 409 `image_not_available` with the catalog's reason, and `blank` or nothing is today's request. The parent sends `bundle` to a helper only for a ready image other than `blank`. A free `image` name from the browser is refused with a 400; the helper's `image` field comes only from the machine's own saved default.
- Added without a version change (optional; a helper without it is an older one): `Facts.agent_build`, the lowercase hex SHA-256 of the helper's own program file, worked out once at start (macOS: the running executable; Linux: `/proc/self/exe`). The Root keeps it per machine (replaced by every heartbeat; null when the helper does not say) and returns it as `agent_build` on every machine of `GET /api/machines` and on the machine detail, together with `update`: `{ available, current_build, newest_build, reason }`. `available` is true when the Root has a program for the machine's system (`darwin-arm64`, `linux-x86_64`, `linux-arm64`) whose SHA-256 differs from `agent_build` (an older helper without `agent_build` counts as different, `current_build` null); with no program for that system it is false and `reason` says so in plain words. Panel route `POST /api/machines/{machine}/update-helper` (operator write, 2 a minute per machine) replaces the helper over SSH: answers `{ result: updated | rolled_back | failed, message }`, or 409 `login_needed`, `no_build`, `up_to_date`, `machine_busy`.
- Added without a version change (optional; a helper without them leaves them out): GPU fields in `GET /v1/stats` and the panel stats route: `gpus[].vendor` (`nvidia`, `amd`, `apple`, `intel`, `unknown`; any other text becomes `unknown`), `power_watts`, `power_limit_watts`, `fan_percent`, `clock_mhz` and, NVIDIA only, `processes` (up to 8 programs holding GPU memory). At most 8 GPUs (was 16). The parent drops a number outside its range, it never clamps. The history points carry a per-GPU series (`gpus[]` with `index`, `utilization_percent`, `memory_used_bytes`, `temperature_celsius`, `power_watts`). See `docs/monitor-contract.md`.
- Added without a version change (optional; a helper without it answers 404 and the parent then shows the keys as not applied): SSH keys per VM. Helper `PUT /v1/workloads/{id}/ssh-keys` with the full key list (`{ "keys": [...], "install_sshd": bool }`, at most 20 keys) writes `/root/.ssh/authorized_keys` inside the VM and answers `{ "applied", "sshd", "installed" }`. `install_sshd` (optional, default false) makes the helper also install the SSH server if missing, lock it to keys only and start it (up to 5 minutes; keys are written first). `installed` is in the answer only when `install_sshd` was true. A failed install is a 502 with code `sshd_install_failed` and a plain message; the keys are kept. Panel routes `GET` and `POST /api/machines/{machine}/workloads/{workload}/ssh-keys`, `DELETE .../ssh-keys/{key}` and `POST .../ssh-keys/retry`; the view carries `keys` (never the key itself), `applied`, `sshd`, `sshd_state` (`idle`, `installing`, `failed`), `sshd_message` and `connect` (`jump`, `jump_is_default`, `vm_address`, `command`). The machine setting `ssh_jump` (`user@host[:port]`, set with `PATCH /api/machines/{id}/settings`) is the address the laptop uses to reach the machine and builds the `ssh -J` command. See `docs/ssh-keys.md`.
- 1.3.0 (additive): `Facts` carries `agent_version` (the same text as `/v1/health`) and `engine` (`name`, `version` or null, `ready`); `POST /v1/bundle/uninstall` turns the chat off on the machine or in a workload and keeps its conversations; command type `bundle_uninstall`. The Root accepts a helper that does not say these (they stay null in the panel); an Agent that claims 1.3.0 must.
